# Bitewise 演示与数据准备说明

## 结论

上台演示至少准备两条路径：

1. **可重复 Demo**：点击 `Demo · Use prepared menu`，直接载入固定菜单、风险结果和餐厅数据；相机和上传入口仍然保留，用于展示“真实输入也支持”。录视频只走这一条路径，避免网络、OCR 或现场输入造成结果漂移。
2. **现场试用**：使用真实相机/上传菜单，现场输入自己的 Food Passport。现场试用和 Demo 不共用会改变结果的状态；当前账号、Food Passport、收藏餐厅和邀请状态保存在浏览器 `localStorage`，适合单设备课堂试用。

## Find Food 数据包

`public/data/restaurants.json` 与 `src/App.tsx` 中的餐厅目录以复旦大学管理学院政立路 558 号为中心，覆盖约 0–3 km 的政立院区、政立路、合生汇和五角场线索。每条记录含分类、距离、地址线索、推荐原因、来源备注和本地代表性图片路径；前端当前直接使用同一批内置记录，JSON 文件作为可交给后台/后续 API 的种子数据。

当前记录的用途是课堂 Demo 数据，不是对营业状态、评分、门牌、菜单或过敏原的保证。`到店前请核对` 的记录必须在演讲前由团队现场核验一次，并补上核验日期、营业时间和最终门店楼层。图片是项目自有的代表性插画，不冒充商家官方照片；如果之后取得商家授权照片，可只替换 `photoSrc`。

## 食物知识库

`public/data/chinese-food-knowledge.json` 由 `scripts/generate-food-knowledge.mjs` 生成，目前有 **520 道菜、10 个菜系/餐厅类型**。每道菜包含：

- 常见原料与常见过敏原；
- 可能过敏原（酱料、汤底、共享厨房带来的不确定性）；
- 饮食信号（肉类、辛辣、可能的素食误判）；
- `common recipe pattern` 证据等级与安全边界说明。

这个库可以支持“菜名 → 典型原料 → 需要向餐厅确认的点”的演示与后端规则。它不能替代餐厅级配方确认；严重过敏时必须把“未知/可能含有”升级为询问餐厅，而不是推荐安全。

## 是否需要课堂用户数据库

当前阶段不需要为了“看起来 ready”接入 Firebase。单设备课堂演示用 `localStorage` 足够，也更容易在每次演示前一键重置。建议按以下顺序升级：

- **课堂试用前**：只收匿名 session id、语言、选择了哪些功能和错误日志；Food Passport 默认只存本机，不上传真实过敏信息。
- **需要多设备同步时**：再接 Supabase 或 Firebase Auth + Firestore，并增加明确同意、删除账号、数据保留期限和最小化字段。优先存过敏原 id 与严重程度，不存不必要的姓名、精确位置或原始照片。
- **正式上线前**：把餐厅、菜品和过敏原从 `App.tsx` 拆成服务端/后台可编辑表，保留 `sourceUrl`、`verifiedAt`、`photoLicense` 和 `confidence`，让每条安全结论可追溯。

## 演讲前验收标准

- 录屏版连续走完：Home → Demo 菜单 → Food Passport 冲突 → Ask restaurant → Add to order → Split bill → WhatsApp 分享文本。
- 现场版连续走完：打开相机/上传 → 得到菜单结果 → 修改 Food Passport → 重新查看风险；准备一张清晰菜单照片和一张失败/模糊照片作为备用。
- Find Food 的六个意图都能显示对应餐厅，不会跳回 Scan；Save 后右侧状态和数量即时更新。
- Split bill 的分享文本包含参与者金额、菜品归属和每道菜金额；分享只打开 WhatsApp 预填文本，不自动发送。
- 录屏前清空测试邀请、收藏和课堂试用状态，点击 Demo 后不要临时改数据。
